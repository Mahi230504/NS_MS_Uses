The three "obvious" ways to automate a phone — all dead ends
✗ APPROACH 1

Per-app APIs

Don't exist for most consumer apps. Need partnerships, break on every release. Doesn't scale to "any app."

✗ APPROACH 2

RPA / coordinate scripts

"Tap (540, 1200)." Brittle. One UI update and every hard-coded tap is wrong. Maintenance nightmare.

✗ APPROACH 3

Accessibility-service hacks

Invasive, per-app, fights the OS, trips fraud detection. Fragile and adversarial.

Every one of these tries to reach inside the app. That's the trap.

Walk each, kill each. The common failure: they all try to integrate with the app's internals. Set up the pivot.
The pivot

Stop integrating. Perceive.

Treat the phone the way a human does:
look at the screen → reason → tap. One loop, every app.

This is "computer use." No integration surface at all — the screen is the API. The same agent drives a grocery app, a maps app, a chat app, because it never assumes anything about the app's internals.
Why now? This was science fiction 3 years ago. It only became viable when vision-language models got good enough to read a UI and pick the next action. The model is the new ingredient — the rest is engineering.

From 300 nodes to ≤60 useful elements

def parse(xml, profile=COMMERCE) -> list[UiElement]:
    root = ET.fromstring(xml)
    parent_map = {c: p for p in root.iter() for c in p}
    for node in root.iter("node"):
        bounds = _parse_bounds(node.attrib.get("bounds"))
        # keep only clickable / labelled / focused, non-zero-area
        if not (clickable or text or desc or focused):
            continue
        cx, cy = (x1+x2)//2, (y1+y2)//2     # CENTER = tap target
        is_action = _is_action_like(text, desc, rid, profile)
        if is_action:                       # walk parents → product title
            container_label = _find_container_label(node, parent_map, profile)
        ...
    return _suppress_wrapping_clickables(elements)  # drop the card,
                                                    # keep the inner ADD

Five decisions that make grounding work:

  • Center coords from bounds — the model taps these, never raw pixels.
  • Keep only clickable / labelled / focused nodes; drop layout wrappers & zero-area.
  • Suppress wrapping clickables — a card wrapping an ADD button tempts a tap on the card (opens detail). Force the inner target.
  • 60-element budget, with every [ACTION] & [CART] pinned first so they're never truncated.
  • Profile-driven tags — commerce apps get the shopping vocabulary; everything else pays nothing.
The wrapping-clickable suppression is a subtle, real bug they'd hit: tapping a product card opens the detail page instead of adding. Leaf-preference fixes it.
DEEP DIVE · the product-label trick

Why each "ADD" knows what it buys

In Blinkit's tree the product title lives on a parent ViewGroup's content-desc, not on the ADD button. So we walk up the XML from each ADD until we find a real label.

def _find_container_label(action_node, parent_map, profile) -> str:
    cur = parent_map.get(action_node)
    while cur is not None:
        for candidate in (content_desc(cur), text(cur)):
            if candidate and candidate.lower() not in profile.action_desc_exact \
               and len(candidate) >= profile.min_container_label_len \
               and fits_inside_a_card(cur):        # not the whole screen root
                return strip_re.sub("", candidate) # "…is available for ₹130" → ""
        cur = parent_map.get(cur)
    return ""
Real failure this prevents: the model claimed "tap ADD on eggs" but the coords actually bought a Fire TV Stick. With the label attached, a guard catches the mismatch before the tap. (We'll see that guard in Layer 5.)

DEEP DIVE · device/adb_controller.py

Driving a real, hostile device

🌳 The 3-pass UI dump

uiautomator dump needs the screen "idle" — but carousels & skeleton loaders never idle. So:

  1. normal dump (full fidelity, incl. EditText)
  2. retry after 250 ms (let it settle)
  3. --compressed fallback (works on animated screens)

Writes to /sdcard then cats it back — streaming to /dev/tty hangs on ColorOS. 8 s cap per pass.

🧩 OEM reality checks

  • ADBKeyboard IME swapped in for a task — input text drops chars in a focus race; restored on exit.
  • wake_screen() first — a sleeping display returns all-black PNGs the model can only "wait" on.
  • foreground package read via 3 fallbacks — ColorOS hides it behind the notification shade.
  • Every adb call is timeout-bounded so a stuck USB link can't freeze the whole loop.

Every one of these lines exists because a real run failed without it. ← that's the whole talk in one sentence.

This slide is pure "the engineering is the hard part" evidence. Each workaround maps to a real device that misbehaved. Production is a thousand of these.
LAYER 5 · THE GUARD STACK

The model proposes. The harness disposes.

The model is wrong all the time. Every proposed action runs a gauntlet before it can touch the device:

Hard vs soft. validate is a hard fail — a blocked action ends the task. The 11 guards are soft: a rejected action appends a corrective hint to history and the model retries next step. It never reaches the phone. It self-corrects with feedback instead of failing.

DEEP DIVE · one guard, in full

Product-name mismatch — "you said eggs; that buys a Fire TV Stick"

def _add_product_name_mismatch(action, elements) -> str | None:
    note = action.get("note", "")                       # "tap ADD on eggs"
    claimed = _extract_product_from_add_note(note)       # "eggs"
    words = significant_words(claimed)                   # drop stop-words
    x, y = action["x"], action["y"]

    target = find_action_at(x, y, elements)              # the [ACTION] under the coords
    if target and target.container_label:                # ground truth from the XML
        if any(w in target.container_label.lower() for w in words):
            return None                                  # ✓ claim matches the card → allow
        return (f"note claims ADD on '{claimed}', but the button at "
                f"({x},{y}) actually buys '{target.container_label}'. "
                f"Find the [ACTION] line whose for \"...\" matches.")   # ✗ REJECT + hint
The pattern every guard follows: read the model's stated intent (note) → check it against structural ground truth (the UI tree) → on conflict, return a specific, actionable hint. The model reads the hint next step and re-targets.
Conservative on purpose: it skips when the product can't be parsed, when there's no label, when the tree is empty. A guard that mis-fires is worse than no guard — false rejections stall real tasks.

DEEP DIVE · self-correction & cost control

Three uses of one perceptual hash

♻️ Dedup

Screen identical to what the model last saw? Skip the model call, synthesize a wait. Saves tokens & latency (capped at 3 in a row).

✅ Verify

⚙️ AppProfile — the structural half

The vocabulary the UI-tree renderer uses to tag elements, and the toggles that arm the shopping guards. Two profiles today:

  • GENERIC — inert. No tags, all shopping guards off. Pays nothing. (maps, chat, media, rides…)

You don't code generality per app. You code the loop once, and declare what's special.

    enforce_shopping_guards: bool = False   # arms the 8 commerce guards
    action_text_tokens: frozenset = ...     # what counts as [ACTION]

    # ...vocabulary for the renderer's tags

GENERIC  = AppProfile(name="generic")               # everything empty → inert
COMMERCE = AppProfile(name="commerce",
    enforce_shopping_guards=True, action_text_tokens={"add","+","checkout",...}, ...)

    return _BY_PACKAGE.get(package, GENERIC)         # unknown app → GENERIC

Defensive by construction · seven independent layers

The safety model

1 · Emulator-only by default
refuses to run if a physical device is attached unless ALLOW_PHYSICAL_DEVICE=1 — and warns loudly
2 · Authorization
only users in users.json; onboarding via 5-min single-use /pair codes; per-user policy: read-only / confirm-sensitive / always-approve
3 · Action validator
allow-set + blocklist (no calls, SMS, factory-reset, uninstall, rm) — hard fail before execution
4 · HITL gate
payment / OTP / delete / permission + any model need_approval — blocks until you tap
5 · Audit before action
EXECUTING logged before the act, RESULT after — keys/tokens redacted, daily rotation
6 · Webhook security
timing-safe shared secret; bound to 127.0.0.1, reached only over the USB adb reverse tunnel; empty secret = disabled

7 · Secrets never touch disk or logs — all config from .env; keys regex-redacted from the audit trail.

The gate is just detection + a blocking wait

async def requires_approval(action, screenshot_b64, policy) -> bool:
    if policy == "read_only" and action_type in STATE_CHANGING:
        raise ReadOnlyViolation(...)        # hard refusal, not a prompt
    if policy == "always_approve":  return False
    if action_type == "need_approval":  return True   # model asked → always pause
    # scan the model's plain-English `note` for sensitive intent:
    haystack = note + reason + summary + text
    return any(kw in haystack for kw in SENSITIVE_KEYWORDS)  # payment/otp/delete/permission

async def wait_for_approval(user_id, timeout=None) -> bool:
    event = asyncio.Event(); self._pending[user_id] = event
    await asyncio.wait_for(event.wait(), timeout)     # ← orchestrator blocks here
    return self._results.get(user_id, False)          # grant()/deny() set the event
Two doors to "yes." A keyword scan of the model's narration OR (optional, ENABLE_VISION_HITL=1) a vision yes/no classifier — cached by phash so a static screen doesn't burn a call. The two results are OR'd: either one pauses.
Why a keyword scan of the note? The model writes "tapping Place Order" in plain English. Catching dangerous intent stated in words is a cheap, robust second net beyond the action type alone.
The asyncio.Event bridge between the orchestrator coroutine and the Telegram callback is the elegant core — no threads, no polling. grant()/deny() in the handler set the event the loop is awaiting.
